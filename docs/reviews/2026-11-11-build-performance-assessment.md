## Ranked findings and disposition

1. **Production persistent cache: accepted optimization candidate; implementation pending direction.** `webpack.production.ts` sets production mode and source maps and exports five configs, with no filesystem cache. Development already applies filesystem caches with distinct `development-${index}` names. Add per-compiler production filesystem caches outside `out` and package outputs, local to each worktree, with complete configuration/dependency invalidation. Include environment-sensitive replacement inputs, target/architecture/channel and build identity correctly; app-info.ts embeds build version and SHA, so changed identity must rebuild affected modules. Benchmark identical-source warm rebuild and realistic one-file/new-version rebuild separately. This targets repeated builds, not the first cold build; no speedup magnitude is established. Do not share mutable webpack cache across worktrees merely because root node_modules is a junction.

2. **Repeated TypeScript program/checking: accepted investigation candidate; requires guarded implementation.** Common config uses ts-loader with no options for main, renderer, crash and CLI. Root tsconfig includes app/**/*.ts and app/**/*.tsx, including test sources, and excludes highlighter; highlighter uses its own tsconfig. Installed ts-loader defaults `transpileOnly: false` and `onlyCompileBundledFiles: false`. Thus each compiler can load/check a broad TypeScript program. Explore transpile-only bundling plus one explicit fail-closed application typecheck and one highlighter typecheck, optionally incremental with separate state. Preserve syntax/semantic diagnostics, production error gates and existing root coverage; do not simply remove checking or silently exclude tests to obtain better times. Measure to establish how much repeated program/checking contributes relative to minification. This is a plausible cold- and warm-build improvement, not measured proof.

3. **Always-on bundle analysis: accepted low-risk optimization candidate.** Production renderer always instantiates BundleAnalyzerPlugin to emit a static HTML report, openAnalyzer false. Make analysis an explicit opt-in diagnostic command/flag using strict true parsing. Keep bundling and runtime syntax checks; removing analysis does not fix invalid generated JavaScript (the pasted import.meta error reflects a separate previously diagnosed bundle defect). The report is not required in the app; build.ts moves it away and package-local excludes it. Expected saving is unmeasured and may be small relative to compilation.

4. **Use existing development iteration for routine code work: informational, already available.** package.json provides build:dev/start; development has persistent filesystem caches, and start.ts serves renderer through webpack development/hot middleware, builds other processes to disk and stages resources without packaging. This avoids production minification and repeated executable packaging for renderer iteration. Full production-like packaged acceptance remains necessary for packaging/release-specific changes. Development runtime differs from production and main-process changes require an appropriate rebuild/restart; do not present hot reload as release acceptance.

5. **Repeated resource/runtime staging: accepted later optimization candidate, timing prerequisite.** build-local always invokes webpack, build.ts staging, then package-local. build.ts deletes/repopulates out/node_modules, runs a filtered npm install, recopies Git, native helpers, emoji and static resources, and regenerates licenses. package-local copies installed Electron and entire prepared out into a fresh staging folder, then promotes it. It already reuses installed Electron: recommending an Electron download cache would miss this local path. Consider content-addressed reusable immutable resource staging or incremental copies keyed by dependency lockfiles, native ABI/architecture, resource/submodule content and build-tool changes. Retain destination deletion reconciliation, license/Sass gates, atomic final promotion, ownership receipts and source identity checks. Avoid writable shared out/dist between worktrees. Not first priority until stage measurements show significant cost.

6. **Parallelism/memory and minifier/source-map changes: deferred pending measurements.** Five configs already use webpack's multi-compiler export; parallelism is not absent. Increasing it or heap size blindly can worsen contention. build-local uses 8192MB heap while compile:prod uses 4096MB; neither setting proves the process is memory limited. Production uses source-map and default production optimization/minification. An optional fast preview profile could reduce these costs but changes debugging/output characteristics, so preserve standard production behavior. Measure stage/CPU/memory use and cold/warm profiles before changing concurrency, replacing the compiler/minifier or disabling maps.
